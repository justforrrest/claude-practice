# 임상 질문 로그 시스템 — 설계 문서

이 문서는 Claude Code가 읽고 구현을 시작하기 위한 설계 브리핑이다.
사용자(한의사, 1인 원장)와의 설계 논의에서 확정된 결정과 그 **근거**를 담았다.
구현 중 판단이 필요할 때는 아래 "설계 철학"으로 돌아가서 방향을 잡을 것.

---

## 1. 이 시스템이 존재하는 이유 (가장 중요 — 여기서 벗어나지 말 것)

사용자는 매일 환자를 진료하지만 **경험이 지식으로 압축되지 않는** 정체감을 느낀다.
필요한 것은 공부 계획이나 통계 대시보드가 아니라, **하나의 임상 질문이
던져지고 → 가설이 서고 → 고민이 꼬리를 물고 → 진료에 적용되고 → 반응이
기록되는, 그 "질문의 일생"이 한눈에 보이는 시스템**이다.

핵심 감각 세 가지:
- **case를 돌아본다** — 출발점은 논문/커리큘럼이 아니라 오늘 본 환자다.
- **임상 질문을 던져 놓는 것이 엔진** — 질문이 먼저 쌓이고 거기서 자란다.
- **"쌓이는 것"이 눈에 보여야 한다** — 축적의 시각적 확인이 정체감을 푼다.

> 구현이 이 세 가지에서 멀어지면(예: 통계 기능, 정량 registry, 공부 일정 관리로
> 무게중심이 옮겨가면) 방향이 틀린 것이다. 이건 **질적 회고 도구**이지
> 양적 추적 도구가 아니다.

## 2. 확정된 데이터 구조 결정

- **환자 식별정보는 넣지 않는다 — 익명 전용.** 발단 칸에는 임상 정보만
  들어간다(예: "68F, L4/5 stenosis, 보행거리 감소"). 이름·차트번호·생년월일
  등 식별정보는 어떤 칸에도 쓰지 않는다. 덕분에 개인정보 보호 장치가 불필요하고,
  실행 환경 선택이 자유로우며, 나중에 Claude에게 통째로 넘겨 회고하기도 안전하다.


- **저장 형식: 마크다운 파일.** 질문 1개 = 파일 1개. 앱은 이 파일을 읽고 쓰는
  UI 역할. 사용자는 마크다운을 직접 편집하지 않는다 — **화면에서 버튼/입력으로
  다루고, 저장만 .md로** 된다.
  - 이유: 몇 년에 걸친 개인 임상 자산. 앱이 없어져도 폴더만 열면 읽혀야 한다.
    옵시디언 등 외부 도구로도 열람 가능해야 하고, 나중에 Claude에게 통째로
    넘겨 "쌓인 질문들 훑어봐"가 가능해야 한다.
- **나중에 SQLite로 이전 가능하도록 설계할 것.** 그래서 각 파일 상단에
  **YAML frontmatter**로 구조화 메타데이터를 반드시 넣는다. 이 필드들이
  나중에 그대로 DB 칼럼이 된다. 파싱 가능한 일관된 형식을 엄격히 지킬 것.

## 3. 질문 파일의 구조 (질문의 일생)

순서가 중요하다: **발단 → 가설(버전으로 누적) → 고민 로그(날짜별) → 적용 →
반응 → 현재 정리**

### 가설을 "버전"으로 쌓는 것이 이 시스템의 특징 (핵심 요구사항)
사용자는 초기 예측 대 최종 결과의 단순 대조가 아니라, **생각이 이동하는
과정 자체**를 남기고 싶어 한다. 그래서 가설은 한 번 쓰고 고정하는 게 아니라
v1, v2, v3...로 누적된다. **각 버전에는 "무엇을 알게 되어 이전 버전에서
바뀌었나"라는 트리거가 붙어야 한다.** 그 트리거가 없으면 학습 기록이 아니라
단순 변경 기록이 된다.

가설 버전 이동 ↔ 고민 로그는 짝을 이룬다: 고민에서 파고들다 생각이 꺾이는
순간이 새 가설 버전으로 찍힌다. 고민은 과정, 가설 버전은 그 과정이 남긴 이정표.

### 파일 예시 (이 골격을 따를 것)

```markdown
---
id: 2026-0001
question: >
  L4/5 stenosis 환자에서 신경학적 결손이 뚜렷하지 않은데 보행거리가 줄 때,
  neurogenic claudication을 어떻게 감별하나?
status: 고민중          # 질문 / 고민중 / 적용중 / 정리
region: 요추
tags: [stenosis, claudication, 감별진단]
created: 2026-09-04
updated: 2026-09-04
---

## 발단
> 68F. 오래된 L4/5 stenosis. 최근 보행거리 감소.
> 하지 증상 심한데 neurological deficit은 뚜렷하지 않음.
(초진 A 항목 등을 붙이는 자리)

## 가설
### v1 · 2026-09-04
neurogenic claudication으로 봄. 자세 의존적 악화가 단서.

### v2 · 2026-09-11
→ 바뀐 계기: 굴곡에서도 완화가 뚜렷하지 않음을 재확인.
혈관성 claudication 배제가 덜 됨. ABI 확인 필요.

## 고민 로그
### 2026-09-04
꼬리를 무는 생각, 찾은 근거, 남은 의문...

## 적용
언제, 어떤 환자에게, 무엇을 바꿔 적용했는지

## 반응
적용 후 실제 경과

## 현재 정리
> 현 시점의 결론 한 문장. 아직 없으면 비워둔다.
> 새 반증이 오면 status를 다시 `고민중`으로 되돌리고 가설 버전을 잇는다.
```

### frontmatter 필드 규약
- `id`: `YYYY-NNNN` 형식, 생성 순번. 파일명도 이걸 기반으로.
- `status`: `질문 / 고민중 / 적용중 / 정리` 4단계.
  - `질문`: 던져만 놓은 상태. `고민중`: 파고들며 가설이 이동 중.
    `적용중`: 진료에 적용해 반응을 보는 중. `정리`: 지금까지를 갈무리(닫는 게
    아니라 현 시점 결론). 이후 새 반증이 오면 다시 `고민중`으로 돌아갈 수 있다.
- `region`: 부위(경추/요추/견/슬/족부/기타 등). 자유 문자열이되 일관되게.
- `tags`: 리스트.
- `created` / `updated`: `YYYY-MM-DD`. 파일 수정 시 `updated` 자동 갱신.

## 4. 앱 동작 (구현 범위)

최소 기능:
- 질문 목록 보기 (상태별로 구분되어 보이기 — "쌓이는 것"이 보이는 화면)
- 질문 하나 열어서 읽기 (일생 전체가 시간순으로)
- 새 질문 만들기
- 기존 질문에 **가설 버전 추가** / **고민 로그 항목 추가** (날짜 자동)
- 상태 변경

각 편집 동작은 뒤에서 해당 .md 파일을 정확히 수정한다. 특히 가설/고민 로그는
**기존 내용을 보존하며 새 항목을 올바른 섹션에 끼워넣어야** 한다(덮어쓰기 금지).

> 화면 부가 기능(태그 필터, '고민중'만 모아보기, 오래 방치된 질문 상기 등)은
> 아래 미결정에서 확정 후 반영.

## 5. 설계 철학 (구현 판단의 기준)

- 입력 마찰이 낮아야 지속된다. 진료 사이/진료 후 잠깐에 쓸 수 있어야 한다.
- 그러나 이 시스템의 목적은 "가볍게"가 아니라 **"축적이 보이게"**다.
  둘이 충돌하면 축적 가시성을 우선한다.
- 데이터 영속성 > 기능 화려함. 파일은 사람이 읽을 수 있게, 형식은 오래 살아남게.

---

## 6. 아직 정하지 않은 것 (사용자와 확정 후 채울 것)

- [ ] **화면 부가 기능** 범위 (태그 필터 / '고민중'만 모아보기 / 오래 방치된
      질문 상기 등). 어디까지 초기 버전에 넣을지.
- [ ] **실행 환경** — 원장실 컴퓨터 1대 로컬 브라우저 앱을 기본안으로 제안 중.
- [ ] 기술 스택 — 사용자의 Claude Code 숙련도 확인 후 결정.

## 7. 확정된 사항 요약 (빠른 참조)

- 저장: 마크다운 파일 1질문 = 1파일, YAML frontmatter 필수, SQLite 이전 대비.
- 질문 일생: 발단 → 가설(v1,v2,v3 트리거 포함) → 고민 로그(날짜별) → 적용 →
  반응 → 현재 정리.
- status: 질문 / 고민중 / 적용중 / 정리 (정리 후 반증 시 고민중 복귀 가능).
- 개인정보: 익명 전용, 식별정보 일절 없음.
- 목적: 질적 회고 + 축적의 가시화. 통계/정량 추적 도구 아님.
```
